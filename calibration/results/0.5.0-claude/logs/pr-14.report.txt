Confirmed (3):
- [CRITICAL] src/interest.js:30 (4 sites) Local-vs-UTC day mismatch double-credits interest (corrected)
  The skip check compares a UTC-derived stored day against a locally-formatted 'today', so on any server not running in the UTC timezone the hourly job re-credits interest instead of skipping already-credited accounts.
  failure: On a server not running in UTC (e.g. TZ=Asia/Kolkata, UTC+5:30), during the hours each day when the local calendar day has rolled over but the UTC day has not, every hourly accrueInterest tick computes dayOf(clock()) as the new local day while the account's lastAccruedOn still holds the previous UTC day, so the 'already credited today' check never matches and the account is credited again on the next hourly tick within that window, duplicating interest.
- [HIGH] src/server.js:162 Hourly job blocks event loop under load (corrected)
  The setInterval callback runs accrueInterest's single-threaded, unbatched for-loop over all accounts synchronously inside the HTTP server's event loop, with no bound on how long that can take, so every concurrent request stalls for the job's full duration once an hour.
  failure: With N accounts in the store and at least one not yet credited for the current day, calling the hourly setInterval's callback (accrueInterest(store) at src/server.js:163) runs synchronously on the Node event loop; any HTTP request already in flight or newly arriving during that window is delayed by the job's full runtime (empirically ~2.65s for 30k accounts, worse for more, growing super-linearly because each credited account triggers an O(n) store.update scan).
- [HIGH] src/server.js:162 Hourly timer races request handlers' store.save() (corrected)
  store.save() writes to a fixed per-process tmp path, not a per-call-unique one; the new hourly timer calls it from the same process as every mutating route handler's inline save, and concurrent calls reliably collide.
  failure: Two store.save() calls overlapping in the same process (e.g. the hourly timer's save racing a concurrent request handler's inline save) share the literal tmp path `${file}.${pid}.tmp`; whichever rename() runs second gets ENOENT because the first already moved that shared tmp file to the real path. If the request handler's save loses, the client gets a false 500 for a mutation that already committed in memory, inviting a retry that creates a duplicate deposit/transfer (no idempotency key exists). If the timer's save loses, that hour's interest credit stays unpersisted and lastAccruedOn already marks the account as done for today, so it isn't retried until some other save happens to flush the whole store; a restart before that happens loses the credit.
